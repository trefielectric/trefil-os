# Seguridad y estado verificable

La demostración web guarda datos ficticios en el navegador. La selección de roles allí permite probar el flujo; **no representa una sesión ni permisos empresariales reales**. El libro PostgreSQL preparado es independiente. Para operar con datos reales hay que conectar la autenticación, el adaptador de datos y Storage y repetir las pruebas de extremo a extremo con usuarios personales.

## Autorización del backend

- El acceso financiero requiere `auth.jwt()->>'aal'='aal2'` en `private.has_access`: una sesión de contraseña sin segundo factor no puede leer ni alterar información financiera, ni siquiera siendo propietario. La tercera migración aplica esta condición a las mismas políticas de empresas, sedes y Storage.
- RLS está activado en las 28 tablas de negocio expuestas; `anon` no recibe acceso a tablas ni RPC. Los usuarios autenticados reciben únicamente `SELECT`, filtrado por empresa, sede, rol y estado de perfil/membresía.
- `organization_members` y `profiles.active` son la autoridad. Las funciones consultan estas tablas en cada operación. No usan `user_metadata`, roles enviados por el navegador ni afirmaciones de rol que puedan estar desactualizadas en el JWT.
- `owner`, `admin`, `treasury`, `accounting` y `auditor` tienen lecturas financieras según su ámbito. Inventarios, producción, ventas, RR. HH. y empleados tienen roles preparados, sin acceso financiero implícito. Auditor no puede escribir.
- El navegador no puede insertar, modificar o borrar tablas directamente, tampoco un propietario. Las escrituras pasan por RPC públicas `SECURITY INVOKER` que llaman implementaciones revisadas en `private`.
- Las implementaciones privilegiadas requieren `auth.uid()` válido, perfil y membresía activos, sede válida y rol suficiente. Usan `search_path=''`, nombres totalmente calificados, entradas validadas y permisos de ejecución explícitos. No se debe exponer `private` en la configuración de Data API.
- La revocación de una membresía o perfil es efectiva inmediatamente aunque quede un JWT vigente. El cierre de sesión y la revocación de sesiones también deben verificarse al conectar Auth; este proyecto local no ha probado GoTrue remoto.

El umbral inicial de aprobación es COP 5.000.000. Toda apertura, ajuste, gasto personal, pago de deuda y reverso exige revisión de otra persona, incluso por debajo del umbral. Administración o propiedad pueden decidir; contabilidad puede registrar y conciliar, sin aprobar. El solicitante no puede aprobar ni rechazar su propia operación. Las cuotas proyectadas no generan pagos y no se aceptan movimientos con fecha futura como realizados.

Las partidas se insertan mientras el movimiento está pendiente. Luego no pueden agregarse partidas a uno contabilizado; las existentes nunca se editan o eliminan. Los originales contabilizados, soportes, condiciones de deuda, pagos, conciliaciones y eventos de auditoría preservan el historial. Un operador con control superusuario puede desactivar triggers; por eso la continuidad exige acceso mínimo, auditoría del proveedor, respaldos fuera de la base y verificación de restauraciones.

## Storage privado

El agente principal creó mediante el panel institucional el bucket `financial-supports` con `public=false`, límite de 10 MiB y tipos `application/pdf`, `image/jpeg`, `image/png`. Una consulta SQL confirmó su privacidad y las dos políticas de lectura/carga. La migración solo define políticas de acceso: no escribe directamente objetos ni buckets en esquemas administrados por Supabase. No se ha declarado verificada la carga/descarga HTTP con usuarios reales.

Ruta obligatoria: `UUID_EMPRESA/UUID_SEDE/UUID_SOPORTE/nombre.pdf` (o jpg/jpeg/png). Los UUID y el nombre se validan; la autorización comprueba el mismo ámbito que el libro. Solo tesorería, contabilidad, administración y propiedad pueden cargar. Auditor puede consultar. No hay política de UPDATE o DELETE ni uso de upsert: una nueva evidencia usa otra ruta. `register_financial_support` exige que exista el objeto y registra su checksum y metadatos. La verificación de contenido, malware, descarga autenticada y rechazo HTTP de objetos ajenos requiere una prueba real del servicio Storage antes de datos reales.

## Identidad institucional y aprovisionamiento

El propietario inicial es `administracion@Trefielectric.onmicrosoft.com`. No hay registro abierto ni asignación automática de propietario al iniciar sesión. `supabase/operations/bootstrap-owner.sql` es una acción manual de operador: exige un único usuario con ese correo ya verificado en Auth, una base vacía y registra la creación. No crea contraseñas, no invita usuarios y no se ejecuta como migración. Después deben invitarse usuarios personales; las operaciones diarias no deben depender de una identidad compartida.

`supabase/config.toml` configura el entorno local: registro y sesiones anónimas desactivados, verificación de correo, rotación de refresh tokens, JWT de 15 minutos y disponibilidad de TOTP. Esto **no prueba ni cambia los ajustes del panel hospedado**. En el panel hospedado ya se guardaron y comprobaron el registro de usuarios desactivado, las sesiones anónimas desactivadas y la confirmación de correo activada. No se crearon usuarios ni se probaron inicios de sesión reales. El resto de los proveedores OAuth, MFA de la aplicación, SMTP, redirecciones exactas y recuperación deben configurarse y verificarse en la cuenta institucional. Microsoft Graph, Outlook, OneDrive y Google Drive no están conectados.

No se almacenan claves en migraciones. Una clave publicable puede residir en variables `NEXT_PUBLIC_*`; `service_role`, claves secretas, contraseñas de PostgreSQL y claves de cifrado jamás deben entrar en el cliente, repositorio, capturas, comandos con argumentos visibles ni resúmenes. Los respaldos y sus claves permanecen fuera de Git. El grupo opcional `trefil_backup_writer` se provisiona manualmente, sin login/contraseña en el script y limitado al UUID de la empresa seleccionada para registrar respaldos.

## Pruebas ejecutadas y límites

`node --import tsx --test tests/database.test.ts tests/provider-rls.test.ts` ejecutó 18 comprobaciones satisfactorias en PostgreSQL/PGlite aislado. La suite financiera aplica las cuatro migraciones y verifica denegación AAL1 y acceso AAL2, RLS en todas las tablas, aislamiento entre empresas y sedes, revocación inmediata, auditor de solo lectura, rechazo de escrituras directas, decimales exactos, doble entrada, clasificación contable, idempotencia con contenido conflictivo, aprobación independiente, traslados compensados, inmutabilidad, reverso exacto y único, reparto/anticipo de capital de deuda y rutas privadas de soporte. Los registros son ficticios y las instancias se cierran al finalizar.

La suite de evento del proveedor crea una función de auto-RLS equivalente a la documentada por Supabase, revoca EXECUTE y comprueba que una nueva tabla creada por el administrador sigue teniendo RLS automático. También conserva definición, OID, propietario y estado del evento; mantiene EXECUTE del propietario y deniega llamadas de `anon`/`authenticated`. La migración es inocua si no existe el helper y rechaza una función ordinaria inesperada con el mismo nombre sin cambiarla.

Los esquemas de Auth y Storage usados en esas pruebas son fixtures mínimos para emular su integración con PostgreSQL. No prueban inicio/cierre de sesión remoto, OAuth, entrega de correos, API REST, carga/descarga HTTP, concurrencia en varios procesos o un respaldo remoto. Tampoco sustituyen a Security Advisor ni un ensayo de restauración de Supabase completo.

La cuenta institucional creó el [proyecto `trefil-os`](https://supabase.com/dashboard/project/kifmqoolaerepvlzrqnk), referencia `kifmqoolaerepvlzrqnk`, en la organización `Trefielectric`, región `sa-east-1` (São Paulo). El usuario confirmó cambio de contraseña y autenticación en dos pasos antes de las operaciones institucionales. El conector Supabase de esta sesión rechazó la consulta de detalles de ese proyecto con «You do not have permission to perform this action», así que el agente principal continuó mediante la sesión institucional del navegador, sin acceder a otros negocios.

El 10 de noviembre de 2026 se ejecutaron las cuatro migraciones desde el editor SQL del proyecto. Una consulta real posterior confirmó 28 tablas de negocio, RLS activado en todas, ausencia de permisos anónimos de lectura, bucket privado y dos políticas de Storage. Esta operación comprueba la existencia y configuración estructural de la base; no demuestra una operación financiera mediante el adaptador de la web.

La ejecución manual en SQL Editor **no registra automáticamente las versiones en el historial de Supabase CLI**. El historial sigue pendiente de reconciliar con las versiones `20261110142435`, `20261110142538`, `20261110144426` y `20261110151745` después de verificar el esquema y autenticar la CLI institucional. No ejecutar `db push` sobre este proyecto sin esa reconciliación: intentaría volver a crear objetos existentes. Usar únicamente el procedimiento oficial de `migration repair` descubierto con `--help`, sobre la referencia institucional exacta, cuando se haya verificado qué archivos fueron aplicados.

La consulta inicial «ninguna función SECURITY DEFINER en public» fue demasiado amplia para un proyecto Supabase hospedado. La consulta real identificó únicamente `public.rls_auto_enable`, con retorno `event_trigger`, `search_path=pg_catalog` y permiso de ejecución anónima por defecto. Esta firma coincide con la [función de activación automática de RLS documentada por Supabase](https://supabase.com/docs/guides/database/postgres/event-triggers). Una función con retorno `event_trigger` no es una RPC ordinaria de negocio: PostgreSQL la ejecuta en el contexto del evento DDL. El vínculo, nombre, estado y propietario del evento deben quedar recogidos en el inventario en vivo; esta coincidencia no autoriza excepciones para otras funciones privilegiadas.

`supabase/operations/verify.sql` distingue las diez RPC de la aplicación —deben existir, ser `SECURITY INVOKER` y negar ejecución anónima— del inventario de funciones privilegiadas del proveedor. El permiso de la función de evento se evalúa separadamente del acceso a RPC financieras. Cualquier función `SECURITY DEFINER` adicional debe revisarse individualmente.

Security Advisor ejecutado en el proyecto real devolvió cero errores y dos advertencias relacionadas con EXECUTE para `PUBLIC`/`authenticated` en `public.rls_auto_enable()`. Para limitar esos permisos innecesarios se preparó y probó la cuarta migración, `20261110151745_harden_provider_rls_execute.sql`: revoca únicamente EXECUTE de `PUBLIC`, `anon` y `authenticated`, sin sustituir la función, cambiar su propietario ni desactivar el evento. Exige la firma exacta `event_trigger`, `SECURITY DEFINER` y un evento enlazado activo; un objeto inesperado provoca rechazo en lugar de modificarlo. La cuarta migración ya se aplicó en el proyecto institucional. Una consulta real confirmó `anon_denied=true`, `authenticated_denied=true` y `event_active=true`. Después de confirmar el REVOKE se creó una tabla de prueba en otra transacción: el evento activó RLS automáticamente; la transacción se revirtió y una consulta confirmó `probe_rolled_back=true` y 28 tablas de negocio. No se conservó la tabla de prueba. La nueva ejecución de Security Advisor desde el navegador institucional devolvió cero errores, cero advertencias y cero sugerencias.

Permanecen pendientes políticas probadas a través del Data API con usuarios reales AAL1/AAL2, invitaciones/permisos personales, auditoría de Auth, adaptador financiero de la web, pruebas reales de Storage, respaldo diario remoto y restauración aislada. Antes del adaptador también deben unificarse restricciones de entrada: el prototipo permite día de pago 1–31 y tasas con ocho decimales; PostgreSQL acepta día 1–28 y `numeric(9,6)` para tasa. Registrar una deuda desde el adaptador necesitará idempotencia además de la ya implementada para asientos/pagos. No se importarán contratos ni datos reales mientras esas diferencias sigan abiertas.

No hay despliegue de producción autorizado como consecuencia de pasar las pruebas locales. Permanecen los requisitos de pruebas de funcionamiento, seguridad y respaldo del sistema conectado.
